Lectiq: Lecture Material Into Graded Practice

Students upload a lecture deck or PDF and get practice quizzes generated from their own material. Every question, and every mark, traces back to the source text.

The Problem & Constraints

Re-reading notes feels productive and measures almost nothing. The tools that do exist, Quizlet and Anki, test recognition, which you can pass by recognising an answer you have seen. Free-response questions actually test understanding, but grading them normally means a fixed answer key, and a fixed answer key cannot know what a student's particular lecture slide actually said.

So the constraint is narrow and strict: any question asked, and any grade given, has to be justifiable against the uploaded document. Nothing from the model's own knowledge of the subject is allowed to leak in.

How It Is Built

Everything runs inside Next.js API routes. There is no separate Python service and no inference server to operate. Document extraction happens client-side: pdfjs-dist for PDFs, and JSZip for PowerPoint, which is simply a zip archive of slide XML. That means the file is parsed in the browser and only the extracted text is ever sent onward.

Topic extraction is a map-reduce over the document, chunked at 10,000 characters, capped at 30 chunks and 60 topics, with a 90-second wall-clock budget. The prompt is explicit that each topic must carry the verbatim original wording of the slides it covers, because that preserved text is precisely what grading is later measured against. The reduce pass merges near-duplicate topics and drops front matter such as agendas, learning objectives, grading policies and thank-you slides. That is the single most effective way to stop a quiz generator from producing a quiz about the syllabus.

Grading splits by question type. Multiple choice is deterministic: the answer either matches what the source says or it does not. Free response is judged by the model against the source, returning a score and short feedback, with context capped at 30,000 characters and the cut marked explicitly in the prompt rather than left silent.

Reliability & Cost Control

Model calls go through OpenRouter with the model selected by environment variable, so the provider is swappable without a code change. Every call runs at temperature 0 for the deterministic paths, retries three times with exponential backoff on 429 and 5xx, and requests response_format: json_object so parsing does not depend on the model remembering to emit valid JSON. Fenced code blocks are stripped before parsing as a second line of defence.

Truncation is a first-class concept rather than an accident. A dedicated limits module carries explicit reason codes: pdf_pages_capped, topics_truncated, deadline_hit. A short quiz is then explainable rather than mysterious. Quota is enforced server-side at ten generated quizzes per user per month, tracked in Postgres by user and month.

Text Summariser: Scoped PDF Extraction

Upload a PDF, choose how much of it to read, and get a summary back as a downloadable file. The working directory is tidied up afterwards.

The Problem & Constraints

Summarising a document is easy; summarising the right part of it is the actual work. A 400-page thesis and the four pages that answer one question need completely different treatment, and a service that only offers "summarise the whole file" is asking the user to do the selection work themselves.

How It Is Built

A FastAPI service with three explicit extraction modes: the full document, a comma-separated list of pages, or a single chapter identified by name or number. Extraction uses PyMuPDF, which handles the text layer directly rather than OCR.

Summarisation runs locally through a Hugging Face transformers pipeline on facebook/bart-large-cnn, with torch for inference. Nothing about the document leaves the machine. The response carries a download link, and the temporary source and summary files are removed once the download is served.

Known Limitation

Summarisation input is currently truncated to the first 1,000 characters, which suits a section or a chapter but means a full-document request effectively summarises only its opening. BART's context window is the binding constraint here; the honest fix is chunked map-reduce summarisation with a reduce pass, the same shape Lectiq uses for topic extraction, rather than raising the truncation limit.

Gohanbako: A Recipe-Sharing API

An account-based API for publishing recipes, where every uploaded image is validated, normalised and re-encoded on the server before it is ever stored.

The Problem & Constraints

An image field on a user-facing model is an unbounded input problem. Users upload whatever is on their phone: PNGs with alpha channels, palette images, files that are not images at all, images large enough to make every subsequent list request slow. Deciding where that responsibility sits is the whole design question.

How It Is Built

The decision here was to handle it in the model's save() rather than in a view or a serializer, so the guarantee holds on every write path including the Django admin and the shell. The uploaded file is opened and verified with Pillow, which rejects anything that is not a decodable image. Alpha and palette modes are flattened to RGB, the image is resized to 800 pixels wide with aspect ratio preserved using LANCZOS, and re-encoded as an optimised JPEG at quality 70 before being written back under a normalised .jpg filename.

On the API side, recipes carry a many-to-many label relation, listing is paginated at ten per page, and filtering is handled by a dedicated filter class. Authentication is Django REST Framework token auth via obtain_auth_token, and registration is a separate open endpoint.
